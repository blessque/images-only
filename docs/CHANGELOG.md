| 2 | 2026-08-09 | **Phase 2 — the grid solver, built and measured in a real browser.** Vite + React 19 + TypeScript 7 (strict, `noUncheckedIndexedAccess`). `solve.ts` is pure and DOM-free: greedy pack by target width fraction, then `H = W / Σaᵢ`, then satisfy the height clamp **by changing row membership** — pulling in or pushing out an image — rather than by cropping. 13 unit tests including a sweep of 60 images × every container width from 320 to 2560 in 7px steps. Three defects the tests caught before they shipped: **(1)** widths were derived from the exact height while the box reported a rounded one, so the box aspect drifted with the aspect ratio (~1.5px on a 3:1 panorama) — a crop, and "never crops" is the one promise. Rounding the height first turned out to be the wrong fix (it shifts Σ off the container by up to 0.5·Σa, forcing 2px width moves), so the height stays **fractional** and only widths are integers; rows stack in normal flow so fractional heights cannot seam. **(2)** the `minRowHeight` floor is unreachable for a single-image row — a lone panorama at 320px genuinely is 107px tall — so the *test* was overstated, not the code; it now asserts the solver breaches the floor only when it provably cannot do better. **(3)** `MAX_ROW_HEIGHT_VH` at 1.0 pulled a second image into every `big` row and so destroyed the grid's only hierarchy mechanism; raised to 1.4, which admits a lone full-width landscape while still catching portraits. **Browser verification (`npm run verify`, playwright-core + system Chrome) found a real bug the unit tests structurally could not**: CLS was 0.03–0.08 despite the docs claiming zero by construction. The first hypothesis — the dev-only async fixture fetch — was **wrong**; simulating the production inlined manifest barely moved it. Instrumenting individual `layout-shift` entries found ONE shift at 184ms attributed to `footer`: `Grid` seeded `containerWidth` at 0 and waited for `ResizeObserver`, so the first paint had no rows and the footer was then shoved down by 42 of them. Seeding from `document.documentElement.clientWidth` synchronously (not `innerWidth` — `clientWidth` excludes the scrollbar) took **CLS to 0.00000 at all four breakpoints**. Also fixed before shipping: `srcset` `w` descriptors must be the file's real pixel width, not the rung number, or variant selection is wrong for every portrait. 42 labelled fixtures generated with ffmpeg carry a border and centred caption so a crop would be visible, not merely measurable. Bundle: 195.77 kB raw / **61.99 kB gzipped** — worth recording because the earlier estimate of ~45KB was low, though it changes nothing about the decision (still roughly a quarter of one photograph). |
| 1 | 2026-08-09 | **Brainstorming and project framework.** Requirements settled, and three contradictions in the original brief resolved rather than papered over. **(1) Drag-and-drop upload vs. GitHub Pages** — Pages is static and has no process to receive a POST, so "where do images live" and "how does he upload" were never two questions. Resolved to a single **Cloudflare Worker** serving static assets *and* the API, with R2 for bytes and D1 for the manifest; $0/mo at this scale, zero egress, nothing to patch. **(2) A-paper cells vs. "never crop"** — the A-series has a fixed √2 aspect, which is exactly what cannot coexist with uncropped photos and no gaps; the user confirmed A-formats were an illustration of *nesting*, not a spec, and they were dropped entirely. Resolved to **justified rows**, `H = W / Σaᵢ`, the only algorithm satisfying never-crop + no-gaps + fills-width + flexible-height together. **(3) ffmpeg** — a CLI binary that cannot run in a browser, and the wrong tool for stills regardless: the dominant quality-per-byte win is not shipping 6000px into an 800px cell, which is a *resize* decision, not an encoder one. Replaced by native `OffscreenCanvas.convertToBlob` in a Web Worker, client-side before upload, which also makes his uploads ~16× smaller. **One non-obvious consequence surfaced and recorded**: within a justified row all images share a height, so widths are locked to aspect ratios — two same-aspect images render identically wide *regardless of size class*. Size class therefore controls row **density**, not size, and Big is `1/1` on desktop (a whole row) dropping to `1/2` on wide screens, which matches the user's own instinct for 2560px. React chosen over vanilla TS **on the roadmap, not on bytes** (forms, more pages, possibly a storefront); recorded explicitly so it is not re-litigated on bundle size. User decided **originals are not stored**, making the 2400px rung the de-facto master — so that rung alone is encoded at ~0.92 vs ~0.86, deliberate asymmetry as bought insurance against a one-way door. Rejected a global "skip compression" toggle as a footgun for a non-technical user, replaced by honest before/after byte counts plus a per-image escape hatch. User chose an opacity-pulse placeholder over the proposed ThumbHash, which **drops a dependency and an upload-time computation** — simpler than what was proposed. Framework copied from `kresti`: `CLAUDE.md`, `.claude/` (permissions + a `UserPromptSubmit` hook auto-injecting the tuning log on grid/compression/auth keywords), `docs/` (architecture, conventions, decisions), `memory/`, all gitignored per the same convention. No application code yet — deliberately, so the taste decisions in the grid could be settled first. |
